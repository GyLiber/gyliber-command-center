# Client Demonstration Baseline

## Purpose

The Command Center is developed as a live product. Each verified production change should become externally visible through the client-accessible application.

## Release loop

```
branch
  ↓
PR
  ↓
CI + security
  ↓
merge to main
  ↓
managed-host deployment
  ↓
live smoke test
  ↓
client-visible progress
```

## Public identity

The application has two URLs conceptually:

1. **Canonical public URL** — owned by GyLiber and suitable for business cards, proposals, client conversations and brand material.
2. **Infrastructure URL** — generated by the hosting provider and retained only for engineering/operations.

The infrastructure URL is intentionally not treated as the product identity.

## Demonstration evidence

Before a client progress meeting, verify:

1. The canonical production URL opens.
2. `/api/health` reports `status=ok`.
3. The visible release matches the intended source revision.
4. The authenticated Command Center loads when member authentication is configured.
5. Live-state information is updating.
6. Recently completed capabilities are demonstrated from the running application.
7. Known limitations are stated explicitly.
8. The next coherent development target is identified.

## Build identity

The authenticated Command Center exposes the running release and deployment commit through its live-state surface. The public surface exposes only the minimum health contract.

## Environment boundary

The initial hosted environment remains a low-risk engineering/demo environment. It is not an authorization to introduce critical company information, production credentials or irreplaceable archives.

## Business-card rule

Only the canonical GyLiber domain should appear on printed material.

Do not print:

- the hosting provider's generated hostname;
- deployment dashboard URLs;
- repository URLs as the primary public address;
- temporary preview URLs.
